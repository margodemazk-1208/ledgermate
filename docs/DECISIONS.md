# Decisions Log (ADR-style)

One entry per major decision made during PRD grilling (see full conversation/PRD v2 changelog for detail). Read this before "helpfully" reverting any of these — each was a deliberate tradeoff, not an oversight.

| # | Decision | Why | Do NOT |
|---|---|---|---|
| D1 | No backend server, no accounts, no login | App is personal + shared informally as APK to <20 friends; original PRD v1 was generic SaaS boilerplate (admin/RBAC/shadowing) that didn't fit this use case at all | Add a server "for sync" without a new PRD revision + explicit user approval |
| D2 | Admin Web Dashboard + Consent-Based Shadowing removed entirely | User's original plan to build this was abandoned before v2; each friend's install is fully independent | Re-add any admin/shadowing concept |
| D3 | Android only, no iOS | Distribution is APK sideload to Android-using friends | Add iOS target/config without being asked |
| D4 | No PIN/biometric lock in v1 | Explicitly descoped for simplicity; may return in v2 | Add a lock screen unprompted |
| D5 | Two Income Frequency modes (Periodic / Daily) instead of one monthly-only model | Real users include both salaried earners (weekly/biweekly/monthly lump sum) and students with daily/irregular pocket money (bekel) — one rigid "monthly" model excludes a real target user | Hardcode a monthly-only assumption anywhere in the formula engine |
| D6 | BR-01 formula is self-balancing (recalculates `RemainingBalance / RemainingDays` on every transaction), not a static once-a-month division | Matches the original intent ("smart" budget) and keeps the number honest after over/under-spending | Replace with a static daily allowance |
| D7 | Goal `currentAmount` auto-accrues daily from `DailySavingsReserve`; withdrawal is allowed and feeds back into available balance | App is a tracker, not a wallet — money isn't physically moved, so the mechanic has to be virtual bookkeeping that stays reversible | Build any real money-movement/wallet feature |
| D8 | Asset/Investment tracking exists in v1 but values are 100% manually updated, never fetched from an API | Matches offline-first principle; "no Open Banking/auto-sync" in PRD excludes automation, not the feature itself | Add a price-fetching API integration without a new decision entry |
| D9 | Notifications are on-device only (`flutter_local_notifications`), never FCM/push | No backend exists to push from; also privacy — nothing leaves the device | Introduce any push notification dependency |
| D10 | Riverpod for state management | Modern default, good codegen ergonomics, team familiarity assumed | — |
| D11 | Repo is public on GitHub | User's explicit choice despite being a personal finance app; code is public, user data never is (no data ever leaves the device, nothing to leak) | Commit any seed/sample data that looks like real personal finances |
| D12 | Visual direction: ENERGY 2 / RHYTHM 2 / MOTION 2 (Stripe/Vercel-balanced) per `docs/DESIGN.md` | User's explicit choice over calm-minimal or energetic-consumer alternatives | Default to generic AI gradient/glassmorphism patterns — see antislop rules referenced in `AGENTS.md` |
| D13 (2026-10-28, M0) | Local DB package is `isar_community` / `isar_community_flutter_libs` / `isar_community_generator`, not the original `isar` / `isar_flutter_libs` / `isar_generator` | The original `isar` packages (last published 2023, maintainer inactive) pin `isar_generator` to `source_gen ^1.0.0`, which cannot resolve alongside current `riverpod_generator` (needs `source_gen ^4.0.0` for Riverpod 3.x on Flutter 3.47.8/Dart 3.13). `isar_community` is the actively-maintained fork with an identical API (`@collection`, `Isar.open`, `IsarCollection`, etc. — only the package/import names change) and a widened `analyzer`/`source_gen` range that resolves cleanly. Verified: `flutter pub add` resolved with no conflicts after the swap. | Add the original `isar`/`isar_flutter_libs`/`isar_generator` packages back without re-solving this exact conflict first — it will reproduce the dependency deadlock |
| D14 (2026-10-28, M1) | Data-at-rest relies on Android's default app-sandbox encryption, not a database-level encryption library | PRD's original claim of "Isar built-in AES encryption" was factually wrong — neither `isar` nor `isar_community` ever had that feature (caught during M1, verified against package docs/changelog). Switching to a DB with real encryption (`hive_ce`, sqlcipher via `drift`/`sqflite_sqlcipher`) was considered and explicitly declined by the user — app's threat model (shared informally to <20 friends, never uploaded anywhere) doesn't justify redoing the M1 data layer | Add an encryption library without a new decision entry; don't re-claim "AES encrypted" anywhere in docs/marketing — `docs/PRD.md` §6.2 corrected accordingly |
| D15 (2026-10-29, M11) | Release Candidate v1.0.0 completed & scope frozen | LedgerMate v1.0.0 finalized with 100% offline architecture, Isar local storage, 6 core screens, and Riverpod state management. Out-of-scope items explicitly deferred to post-v1 per `docs/EXTENDING.md` (PIN/biometrics, iOS support, backend/accounts sync, Open Banking auto-sync, live price APIs, OCR, multi-currency). | Introduce unapproved post-v1 features without a new PRD revision and explicit decision entry |
| D16 (2026-10-29, post-v1.0.0, UI redesign pass) | Multi-Wallet system added as v1.1 scope: new `Wallet` collection (fully user-defined, not fixed Tunai/E-Wallet/Bank types), `Transaction.walletId` (required FK), `TransactionType.transfer` for inter-wallet transfers, and `Wallet.includeInDailyBudget` flag scoping which wallets count toward the Smart Daily Budget Engine (BR-04) | User is redesigning the UI in Figma and the new dashboard mockup includes wallet balance cards (Tunai/E-Wallet/Bank) — grilled via clarify() and confirmed this is a real functional feature, not just a visual mockup. User explicitly wants: (1) fully custom wallets, not fixed types, (2) per-wallet opt-in/out of the daily budget calc chosen at onboarding, (3) inter-wallet transfer support. Wallet balance is computed on-the-fly (`startingBalance` + aggregated transactions), matching the existing `Asset.gainLoss`-style computed-field pattern rather than a stored running balance, to avoid dual-source-of-truth drift. This requires a **data migration** for all pre-v1.1 `Transaction` rows (M0-M11 production data, if any exists on a real device) — a default "Dompet Utama" wallet must be created and every existing transaction backfilled with its `walletId` before the new schema's NOT-NULL constraint can be enforced; this is the first milestone in the project requiring an Isar schema migration on existing data, not just a fresh collection. | Make `walletId` nullable as a shortcut to skip the migration — write the migration step explicitly; don't let Transfer transactions get counted as income/expense in Analytics (FR-07) or the budget formula (BR-01) — they must be filtered out by `type == TransactionType.transfer` everywhere income/expense are summed |
| D17 (2026-10-30, post-v1.1.0, visual + motion system v2) | `docs/DESIGN.md` rewritten wholesale: palette switches from the v1 agent-drafted teal `#0FA37F`/Inter (never confirmed by the user) to the user's own Figma mockup system — dark monochrome base (`#121212`/`#1e1e1e`) + doff burgundy accent `#7d4349` (added as a deliberate "pemanis", not a base color), `Playfair Display` italic for brand/label text + `Space Mono` for all numeric/data text. A full Motion spec (dial MOTION 2, confirmed) is added, grilled explicitly point-by-point with the user rather than assumed: horizontal slide for navigation (Hero/shared-element explicitly declined), count-up/down tween for the daily budget number, slide+fade for new list items, staggered reveal for the FAB speed-dial, scale+haptic for button press, skeleton shimmer for loading states, animated fill for progress bars, and a crafted (non-default) animated-checkmark toast for save confirmations. `docs/design/mockups/` (HTML + PNG + the 2 original user Figma sketches) committed to the repo as the literal source of truth for screen layouts, superseding prose-only descriptions. | User pivoted from directing agent-drafted visual exploration to supplying their own Figma design once M0-M12 backend was stable — per `AGENTS.md`'s "inspect actual source files" principle, the mockup files are the ground truth for layout/color/type, this doc summarizes and points to them rather than re-describing every pixel. Motion was deliberately grilled per-touchpoint (not batch-approved as one dial number) because the user explicitly asked for detailed explanations of each animation technique before picking, per their stated preference for understanding infra/technical tradeoffs before deciding (see USER profile note on explaining technical terms plainly). | Reintroduce the v1 teal/Inter palette without a new decision entry; let burgundy exceed ~10-15% of any screen's visible area (it is an accent, not a base); add Hero/shared-element transitions anywhere (explicitly declined in favor of plain slide); animate widgets outside the touchpoint list above (that's MOTION 3 territory, not what was approved) |
