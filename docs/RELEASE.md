# Release Signing (Android)

Status: infrastructure only. This document and the Gradle wiring in
`android/app/build.gradle.kts` are in place, but **no real production
keystore has been generated by an agent** — a keystore is a durable secret
tied to the human distributing the app, and generating + "securely storing"
one on the human's behalf isn't something an agent run should do silently.
Follow the steps below yourself, once, before the next APK you hand to
friends.

## Why this exists (D18/M17 bug #7)

Every release build before this fix was signed with Flutter's auto-generated
**debug key** (`android/app/build.gradle.kts` hardcoded
`signingConfig = signingConfigs.getByName("debug")`). Android treats
differently-signed APKs of the same `applicationId` as incompatible —
without a stable, real release key, every time the APK was rebuilt (e.g. on
a different machine, or after wiping `~/.android/debug.keystore`), anyone
who already installed a previous build would have to **fully uninstall
first**, losing all their local data (no cloud backup exists in this app by
design — see `docs/DECISIONS.md` D1).

## One-time setup

1. **Generate a real keystore** (requires a JDK; `keytool` ships with it).
   Run this from the `android/` directory so the file lands next to
   `key.properties` (see step 2):

   ```sh
   keytool -genkey -v -keystore release-keystore.jks \
     -keyalg RSA -keysize 2048 -validity 10000 \
     -alias ledgermate
   ```

   You will be prompted for a keystore password, a key password (can be the
   same as the keystore password), and your name/org details (these are
   public metadata embedded in the cert — not secret, but don't need to be
   accurate for a hobby distribution).

2. **Create `android/key.properties`** (copy the template, fill in the real
   values):

   ```sh
   cp android/key.properties.example android/key.properties
   ```

   ```properties
   storeFile=../release-keystore.jks
   storePassword=<the keystore password from step 1>
   keyAlias=ledgermate
   keyPassword=<the key password from step 1>
   ```

   `android/key.properties` and `android/*.jks` are both already in
   `.gitignore` — **never commit either file**. `git status` should show
   neither as tracked after this step.

3. **Store the keystore + password somewhere that survives a lost laptop.**
   This file IS the identity of every future release — losing it means
   every future build is permanently unable to update anyone's existing
   install (same problem this fix solves, permanently, if lost). Options,
   pick at least one:
   - A password manager's secure-file/attachment feature (1Password,
     Bitwarden, etc) for both `release-keystore.jks` and the two passwords.
   - An encrypted backup drive, offline, not synced to the same cloud
     account as nothing else.
   - If distributing via a CI pipeline later: the CI platform's encrypted
     secrets store (e.g. GitHub Actions encrypted secrets), base64-encoding
     the `.jks` file into a secret and writing it to disk + reconstructing
     `key.properties` as a build step — never commit the decoded file.

4. **Build the real release APK:**

   ```sh
   flutter build apk --release
   ```

   Gradle picks up `android/key.properties` automatically (see
   `android/app/build.gradle.kts`) — no extra flags needed. If
   `key.properties` is missing, the build prints a loud Gradle warning and
   silently falls back to the debug key instead of failing — this keeps
   `flutter run --release` working for local development without a
   keystore, but means **a release APK built without `key.properties`
   present must NOT be distributed**. Always check the build log for the
   "WARNING: android/key.properties not found" line before sharing an APK.

## Verifying a built APK is really release-signed

```sh
# Android SDK's apksigner (bundled with build-tools)
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
```

Compare the printed certificate fingerprint against what you expect from
your `release-keystore.jks` (same `keytool -list -v -keystore
release-keystore.jks` fingerprint). If this ever doesn't match a
previously-distributed build, STOP — installing it over an existing install
will force every user to uninstall first.
